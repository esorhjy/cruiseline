# 航程手帳新版介面與使用策略

狀態：2026/11/7。第一、二、三階段已完成實作與本機驗收，範圍與結果見 `UX_PHASE1_2026-11-07.md`、`UX_PHASE2_2026-11-07.md`、`UX_PHASE3_2026-11-07.md`；第四階段仍為規劃。各階段實作不代表已上線。

## 1. 需求與已確認決策

使用者希望既有資料更容易用於四天三夜規劃與船上操作：簡短行程、可替換安排、樓層優先探索、具體攻略分類、快速菜單與英文溝通。

已確認分享方式：由使用者統一修改正式行程，家人查看同一份；臨時替換先存本機。正式發布仍透過專案更新與部署，瀏覽器不持有 GitHub 寫入憑證。

保留航程／船上探索／行前準備三個主畫面，以及菜單與搜尋工具。使用者所說的四個層次是四個工作情境，不必變成四個新主畫面。

## 2. 現況與實際檢查

讀取 PROJECT_BLUEPRINT、CONTENT_RULES、SEARCH_RULES、字級與 notebook 改版規則、9/8 與9/17內容更新，並核對實際資料與 renderer。以本機網站進行 Playwright 390×844 手機模擬與1440×900桌機檢視，操作航程、Deck 10、攻略與菜單。不是實機或線上部署驗收。

| 資料 | 目前實際數量／角色 |
|---|---|
| 行程 | 4 天、38 事件；基本時段、固定／待確認／彈性安排 |
| 設施 | 11 個甲板、45 張卡；部分卡合併多個設施或餐廳 |
| 表演 | 8 張卡；部分卡對應多個節目、場地可變 |
| 攻略 | 7 組、41 張；daily-ops 單組已有12張 |
| 主卡總數 | 132；既有 ID 與連結須保留 |
| 活動查詢 | 550 筆歷史來源及補充紀錄，並非550個當航次可預約場次 |
| 菜單 | 734 筆，含原550筆snapshot；延遲載入並保留餐廳／餐段版本 |

觀察到的具體問題：

- 行程雖有收合，預設仍露出長段第一則說明、用正規表示式挑出的限制與多個連結，難以連續掃讀時間和目的地。
- renderer 對數字開頭時間統一顯示「建議時段」，所以已確認20:15晚餐及08:30公主活動也被錯誤暗示為建議。`planKind` 表達優先程度，不能兼作預約確認狀態。
- 主秀泛稱的關聯連結可能導向某一特定秀，不能以第一個搜尋entity當成每段行程唯一目的地。
- 探索預設45地點全列，先用途再甲板；切「表演」後甲板控制隱藏，無法查看某一層的設施與節目全貌。
- 有些合併卡包含不同區域或多個entity；卡片所在deck、registry的area、活動場地不是可互換的欄位，須逐筆建立清楚關聯。
- 「船上省時省力」混合飲食、購物、照片、App、SPA；「客艙與親子」也混合手環與洗衣。分類名稱不能幫使用者猜出問題在哪裡。
- 部分攻略標題很長，開頭先展示來源標籤和編輯說明，實用動作排在後面。
- 菜單已可用，但從餐廳卡只看到「中英對照」，缺少明確的「看這間菜單」；直接開全部餐廳時要重新找餐廳。

## 3. 導覽與畫面安排

主導覽維持「航程／船上探索／行前準備／菜單」。搜尋常駐頂部。菜單仍開既有查詢面板。

- 航程：選日期 → 讀當日時段列 → 點目的地看詳情；進入調整模式才露出編輯控制。
- 船上探索：內層改成「樓層導覽／實用攻略」。表演和活動加入樓層導覽的類型篩選。
- 行前準備：保留待辦與旅程資料，加入小型行程版本／備份入口；不重貼攻略正文。
- 舊表演與攻略hash仍導向新呈現位置；返回後恢復日期、樓層、分類、展開項與捲動。

### 航程呈現

每列預設只顯示時間／時間關係、中文短名稱、地點、狀態及必要短提醒。英文全名與攻略放到詳情。例：

```text
1/27 海上日                         調整行程
08:30       公主見面會       已確認
            報到地點查預約   查看詳情
合照後      早餐             彈性安排
換裝後      Moana 表演       場次待確認
            Deck 10 船尾     查看表演
20:15       好萊塢聚光燈晚餐 已確認／可能調整15分鐘
            Deck 8 船尾      查看餐廳
```

關鍵短提醒仍保留，例如全員演練、出席資格、需先報名；完整規則在主卡。不可單純裁切第一段或隱藏全部限制。設置 `shortTitle / essentialNote / primaryTarget` 等少量顯示metadata，舊詳細說明先保留於收合內容；已存在主卡的說明逐步改用連結，不一次刪除。

時間確認狀態與優先程度分開：已確認、家庭預留、場次待確認。不從「fixed」或時間字串推定已預約。公主08:30不自行推算結束時間；Moana維持候選。

### 行程替換與儲存

1. 點一天的「調整行程」，每列才出現「替換／改時段／移動／設為備案」。不以拖曳作唯一操作。
2. 點替換，打開共用選擇面板：目前安排 → 依活動／餐廳／設施查找候選 → 顯示地點、資格、資料來源 → 確認替換。
3. 候選來自現有資料ID。合併設施卡要選到具體entity或菜單restaurantId，不能把Pixar、Pizza、Wheezy整組當成一家餐廳。
4. 活動先合併歷史重複場次；保留不同年齡、Open House／正式活動、報名／遊戲的版本。選到資料代表加入家庭計畫，不表示預約完成或當航次有開。
5. 可輸入時間、選早上／下午／晚上、保留「早餐後」等相對順序；未確認的起訖時間不補假值。不自動把歷史sourceTimeHint帶進2027行程。
6. 允許空白休息／自由活動，不強迫每段綁設施。一般項目可調整；已確認晚餐、公主及必到演練預設保護，進階明確確認後才改家庭安排，仍不宣稱已更改DCL訂位。
7. 儲存後顯示「已儲存本機草案」，提供立即復原、逐項還原及整份還原。變更用獨立storage key，不影響清單勾選。
8. 匯出一份有版本資訊的行程檔；匯入先預覽差異，再套用。支援主版本更新時按穩定ID對照；已修改的同一欄若與新版有衝突，讓使用者選擇，不靜默覆蓋。
9. 使用者將匯出檔交回專案，我們核對後更新正式資料、測試與部署。家人開同網址看到正式行程；已有本機草案者須看得出版本差異。

第一版限制在替換、時段、移動、備案與空白休息。跨日插入新項目可沿用同一選擇面板，但不必一次加入拖曳日曆、AI推薦或共同編輯。

儲存採小型 localStorage overlay，資料只存使用者變更與原始版本，不複製全部攻略。儲存失敗必須明示並可匯出；file://繼續可瀏覽，但正式使用建議固定HTTPS網址。本機資料不等同跨裝置同步，瀏覽器資料也可能被清除，匯出備份必須與編輯功能一起交付。依據：[MDN localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)、[瀏覽器儲存保留規則](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)。

### 詳情與回程

第一階段沿用既有主卡與hash導航，從行程點擊後切至對應卡並展開；加「回到1/27行程」並恢復原位置。可預約活動若只有lookup記錄，沿用查詢詳情／Crew面板。不新增另一份正文副本。

餐廳詳情提供「看菜單」，直接帶入restaurantId；必要時選本次餐段。長列表主標題用中文短名，英文名在卡片詳情與Crew中完整保留。若連結有多個可能目的地，顯示可選清單，不能任選第一項。

## 4. 以甲板為第一入口

頁面順序：甲板選擇 → 類型（全部／設施／餐廳／表演活動）→ 該層列表。甲板控制使用一個大且易按的原生選單，顯示「Deck 10 · 花園、快餐與海洋奇緣」。首次預設本次常用Deck 17，之後記住上次選擇；明確標示這是選取樓層，不表示自動定位。可選全部甲板，只有已有資料的樓層列出內容。

單一列表內區分船頭／船中／船尾，未知則標示待核對，不由模糊地名猜位置。區域不是新增一排篩選。收合卡只留中文名、英文短對照、位置、1句用途／限制；詳情保留完整來源與操作。

節目與家庭活動依場館映射進樓層：例如花園舞台 → Avengers，Wayfinder Bay → Moana，Baymax影廳 → 家庭觀影。多樓層劇院可在Deck 6/7都找到同一主卡；Duffy等移動場地標「可能場地，查當航次」，不把兩個地點當成同時演出。

大量活動按同名＋場地＋資格／參加方式合併成活動索引，原記錄保留。一般樓層先列主卡與「此處活動」摘要，展開才載出該場館完整活動；在「表演活動」篩選可查看全部符合項目，不用搜尋引擎top-10限制當瀏覽列表。

只儲存明確 `venueId / deckIds / area / locationStatus` 對照；未有明確樓層的活動留在「全部甲板／地點待確認」及搜尋。地點資料是可查內容，不是船舶定位或即時活動排程。

標題改成可預期問題，例如「房務怎麼點、要等多久」「兒童手環怎麼領與歸還」「禮賓看秀在哪集合」。舊標題作alias。預覽顯示一句結論；展開依序是做法、限制、適用條件、來源。仍標示官方／通知／旅客經驗，但詳細考據不占每張卡的第一行。

主題選擇沿用簡短水平分類列，可橫滑，當前分類顯示數量；不再加任務板、必看清單與第二套標籤。

## 6. 菜單與中英查詢

- 保留目前兩種搜尋模式、全部結果可查、Crew大字卡與返回狀態。
- 從餐廳或晚餐進入，直接選定該餐廳，減少「全部餐廳」重新挑選。合併餐飲卡先讓人選店。
- 菜單先餐廳再餐段／點餐分類；只有該餐廳有多個breakfast／dinner版本時才顯示餐段控制，避免常駐第三排篩選。
- 有可靠既有攻略支持的品項可以顯示短推薦理由和來源；資料庫沒記推薦就正常列菜單，不把收錄等同推薦。份量、口味、年齡、過敏原不自行推定。
- 「給船員看」保留正式英文、所選餐廳與版本；同名菜不因合併丟失餐廳差異。第一版不加入購物車、點單送出或遠端預約。
- 行前準備增加小型「離線資料」狀態與主動下載菜單按鈕，使用者點擊才下載至既有runtime cache。下載失敗可重試、成功後驗證可讀；不在首頁自動載入734筆菜單。

## 7. 視覺方案

方向：現有航程手帳的清楚版，使用原封面、白底、深海藍標題、少量青綠／金色／珊瑚作類型與狀態輔助。狀態必須同時有文字，不能只靠顏色。

- 航程使用輕量時間軸／清單列，不把每段包成厚重卡片；讀完一天時能迅速看出主要安排。
- 地點卡收合時最多名稱、位置、用途短句與必要資格；點開才看詳細內容。少用重複「中文」「Official name」標籤。
- 調整行程按鈕放日期列旁，閱讀模式隱藏操作群；底部主導覽不增加項目。
- 原封面保留完整主體與比例；日期列於往下讀時可固定，不使用自動捲動追蹤時間搶走閱讀位置。
- 維持正文17px、操作16px、輔助至少14px；使用既有字型備援。優先縮短文字與降低重複，保留縮放。
- 沿用CSS Grid/Flex與現有卡片，不新增字型、套件、動畫背景或圖片下載負擔。

## 9. 驗收情境

1. 手機首次進入、切1/27，清楚分辨08:30已確認、Moana待確認及20:15晚餐。
2. 點晚餐→餐廳→該餐廳菜單→英文Crew→返回，日期、餐廳、捲動不丟失。
3. Deck 10同時可見快餐、花園／Wayfinder場地與對應表演；切表演活動不丟樓層。
4. Room Service、手環、洗衣、禮賓看秀各能由問題分類快速找到；保留舊搜尋名稱和連結。
5. 將一段午餐替換成Mowgli，指定暫定時間、刷新、匯出匯入、復原；已確認晚餐不被連帶修改。
6. 未知活動時間、跨樓層／移動場地、未知年齡顯示不確定性，不自動推薦為可用場次。
7. 同名不同資格／場地活動、同名多餐廳菜單仍完整可辨識；734菜單原版本及132主卡ID保留。
8. 儲存被禁用、檔案匯入損壞、版本更新衝突、網路中斷有可理解的處理方式。
9. 360／390手機與桌機、200%文字及間距覆寫；搜尋正常字級結果區至少65%、控制可達。
10. 原資料／家庭行程／搜尋／notebook與字級測試依改動執行；離線測核心與已下載菜單，發布後另驗build與必要資源HTTP200。
